# Перенос боевых данных и замена файлов без потерь

## Коротко

База **не хранится в git** и при выкладке кода не затрагивается, если
соблюсти порядок из раздела 3. Главные риски — не git, а FTP-заливка
папки целиком и `prisma db push` при расхождении схемы.

---

## 1. Сначала — проверить бэкап

```bash
node scripts/inspect-backup.mjs путь/к/elif-backup-2026-10-04.db
```

Скрипт открывает базу **readonly**, ничего не пишет, и отвечает:

- **«БАЗА v2»** — структура совпадает со схемой приложения. Миграция не
  нужна, файл подключается как есть (раздел 3).
- **«БАЗА v1»** — нужен мигратор (раздел 2).
- **«СТРУКТУРА НЕ ОПОЗНАНА»** — разбираем вручную, не трогая оригинал.

Плюс он покажет построчно: сколько записей в каждой таблице, битые внешние
ключи (ученики без класса, оценки без урока), дубли уроков, даты не в
формате ГГГГ-ММ-ДД и недопустимые значения оценок. Это и есть ответ на
вопрос «что совпало».

## 2. Если база v1 — мигратор

```bash
# 1. копия боевого файла, работаем только с ней
cp elif-backup-2026-10-04.db backup/v1-prod.db

# 2. пустая база v2 нужной схемы
DATABASE_URL="file:./new.db" npx prisma db push

# 3. перенос (v1 открывается только на чтение)
node --experimental-strip-types scripts/migrate-v1-to-v2.ts \
  --v1 backup/v1-prod.db --v2 ./new.db --admin-password 'НОВЫЙ_ПАРОЛЬ'

# 4. сверка: цифры должны совпасть с отчётом инспектора
node scripts/inspect-backup.mjs ./new.db
```

Что делает мигратор (`scripts/migrate-v1-to-v2.ts`, 269 строк):

- **v1 не трогает** — только чтение;
- `id` сохраняет 1:1, поэтому ссылки между таблицами не разъезжаются;
- дубли `Lesson(date, classId, subjectId)` схлопывает, выживает первый id;
- нормализует даты (включая Excel-сериалы вроде `46083`) в ГГГГ-ММ-ДД и
  оценки в `5/4/3/2/Н/''`;
- пароли переносит как `legacy_sha256$...`; при первом входе
  `verifyPassword()` молча перехеширует их в scrypt — **пользователи
  входят со старыми паролями**;
- `--admin-password` задаёт админам scrypt сразу (рекомендуется);
- пишет в транзакции батчами по 500: при сбое не остаётся половины.

`--admin-password` стоит задать: иначе у админов останется v1-хеш и в
логе появится WARN.

## 3. Замена файлов на сервере

Порядок важен. Пункт 1 не пропускать.

```bash
# 1. БЭКАП ТЕКУЩЕЙ БОЕВОЙ БАЗЫ (до всего остального)
cp /path/private/gramotagrad.db ~/gramotagrad-$(date +%F-%H%M).db
sha256sum ~/gramotagrad-*.db        # записать контрольную сумму

# 2. выложить код БЕЗ базы и без .env
rsync -av --delete \
  --exclude='.env' --exclude='*.db*' --exclude='node_modules' \
  --exclude='.next' --exclude='backup/' \
  ./ user@beget:/path/app/

# 3. зависимости и сборка
npm ci && npx prisma generate && npm run build

# 4. проверить, что база на месте и цела
sha256sum /path/private/gramotagrad.db   # сумма из п.1 не изменилась

# 5. перезапуск
touch tmp/restart.txt      # Passenger
```

### Почему база переживёт выкладку

- `.gitignore:11-18` исключает `*.db`, `*.db-wal`, `*.db-shm`, `backup/` —
  в репозиторий база не попадает, `git pull` её не перезапишет;
- `.gitignore:21-22` исключает `.env`, поэтому боевой `DATABASE_URL`
  не затирается примером;
- на Beget база лежит **вне DocumentRoot** (`file:../private/...`,
  см. `.env.example`) — её нельзя ни скачать по HTTP, ни задеть заливкой
  папки приложения.

### Три способа всё-таки потерять данные

1. **FTP-заливка папки целиком.** Файловый менеджер перезапишет `dev.db`
   рядом с кодом. Поэтому `--exclude='*.db*'` в rsync обязателен.
2. **`prisma migrate reset` / `db push --force-reset`.** Это стирает базу.
   На боевом сервере — только `prisma generate` и, при изменении схемы,
   `prisma migrate deploy`.
3. **Забыть `*.db-wal` и `*.db-shm`.** SQLite в режиме WAL держит часть
   свежих транзакций в этих файлах. Копировать базу — только вместе с
   ними, либо остановив приложение.

## 4. После переноса — что проверить

```bash
node scripts/inspect-backup.mjs /path/private/gramotagrad.db
```

Сверить с отчётом по исходному бэкапу:

| Что | Ожидание |
|---|---|
| число учителей / классов / предметов | совпадает |
| число учеников | совпадает |
| число уроков | ≤ исходного (схлопнутые дубли) |
| число оценок | совпадает |
| период журнала | те же крайние даты |
| битые внешние ключи | 0 |

Затем вручную: вход под учителем со старым паролем, журнал за известную
дату, отчёт с фильтром по датам, список учеников класса.

## 5. Известное ограничение

`ActionLog.teacher` объявлен с `onDelete: Cascade` (`schema.prisma:186`),
то есть при удалении педагога его журнал действий исчезает. Гард 409 в
`admin/teachers` не даёт удалить педагога с уроками, оценками или
рекомендациями, но педагога, который только входил в систему, удалить
можно — вместе с историей его входов. Лечится миграцией
(`teacherId Int?` + `onDelete: SetNull`), и делать её нужно на машине с
рабочей Prisma — в песочнице бинарники Prisma недоступны. Подробности в
`AUDIT_RESPONSE.md`.
