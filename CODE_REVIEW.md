## 1. Что это за приложение

Next.js 16 (App Router, Turbopack) + Prisma + SQLite. ~4 760 строк TS/TSX, 55 файлов.

| Слой | Файлы | Назначение |
|---|---|---|
| Гарды доступа | `src/lib/auth.ts` | `requireSession` / `requireAdmin` / `teacherHasClass` / `teacherHasSubject` / `hasClassAccess` |
| Сессии | `src/lib/session.ts`, `src/lib/cookie.ts` | серверные сессии, в cookie — raw token, в БД — sha256 |
| Пароли | `src/lib/password.ts` | scrypt N=16384 + бесшовная миграция с v1 sha256 |
| Валидация | `src/lib/validators.ts` | zod-схемы |
| API | 22 route-файла | journal / students / reports / vospitanie / admin / import / export |
| UI | 5 экранов + админка из 8 вкладок | фильтры в URL, zustand только для session/UI |

### Что сделано хорошо

- **Разделение гардов** (`teacherHasClass` для академических разделов vs `hasClassAccess` с учётом `ResponsibleEducator` для воспитательных) — осознанное и аккуратно задокументированное бизнес-правило.
- **Сессии**: в БД только sha256-хеш, `httpOnly` + `SameSite=Lax`, префикс `__Host-` в проде, ленивая чистка протухших, kill всех сессий при сбросе пароля.
- **Пароли**: scrypt с пер-пользовательской солью, `timingSafeEqual`, авто-перехеширование legacy sha256 при первом успешном логине.
- **Нейтральные 403/401** вместо «не найдено» — не даёт перебирать чужие id.
- **Фильтры в URL**, а не в сторе — Back/F5 работают.
- `scripts/migrate-v1-to-v2.ts` написан заметно аккуратнее остального кода: проверяет существование FK, схлопывает дубли, пишет warnings.

### Как я проверял

- Прочитал все 22 API-роута, все гарды, схему, фронтенд, скрипты.
- `npx tsc --noEmit` → **0 ошибок**.
- `npx next build` → **компиляция успешна** (11.3 s); падает только на этапе сбора page data, потому что в песочнице заблокирован `binaries.prisma.sh` и не скачался движок Prisma. Поэтому **прогнать `scripts/test-run.mjs` вживую не удалось** — выводы ниже сделаны статически, но ключевые места я воспроизвёл изолированными скриптами на реальных `zod` 4.5.4 и копиях кода (помечено «✅ воспроизведено»).

## 2. Критические дефекты

### К-1. Отчёты падают с 500 при заполнении поля «Дата до» ✅ воспроизведено

`src/app/api/reports/route.ts:62-73`

```ts
if (dateFrom) {
  lessonWhere.date = { ...lessonWhere.date, gte: dateFrom }
  gradeWhere.lesson = { ...gradeWhere.lesson, date: { ...gradeWhere.lesson?.date, gte: dateFrom } }  // правильно
}
if (dateTo) {
  lessonWhere.date = { ...lessonWhere.date, lte: dateTo }
  gradeWhere.lesson = { ...gradeWhere.lesson?.date, lte: dateTo }   // ← строка 72, БАГ
}
```

Вместо того чтобы положить `lte` внутрь `lesson.date`, строка 72 **заменяет весь объект `gradeWhere.lesson`** на содержимое `lesson.date`.

Прогон точной копии кода (учитель, `classId=1`, период 01.01–31.01):

```
gradeWhere = { "lesson": { "gte": "2026-01-01", "lte": "2026-01-31" } }
```

Два следствия сразу:

1. **Фильтр `classId` потерян** — ограничение по классу из `gradeWhere.lesson` стёрто.
2. **Prisma отвергнет запрос**: `lesson` — это relation-фильтр, у него нет полей `gte`/`lte` → `PrismaClientValidationError` → `handleApiError` → **500 «Внутренняя ошибка»**.

Баг достижим в один клик: `ReportsPage.tsx:94` — обычный `<input type="date">` «Дата до» → `params.set('dateTo', …)` → `/api/reports`. То есть **любой пользователь, который задаст верхнюю границу периода в отчётах, получает 500**. При `type=school` падают сразу `grade.count`, `groupBy` и выборка средних.

Исправление — привести к виду ветки `dateFrom`:

```ts
gradeWhere.lesson = { ...gradeWhere.lesson, date: { ...gradeWhere.lesson?.date, lte: dateTo } }
```

> Отдельно: `TEST_REPORT.md` утверждает «Сценарий 11 Отчёты PASS» и «Сценарий 16: 500 нигде». Тест просто не задаёт `dateTo`.

### К-2. Импорт Excel пишет `classId` в поля `teacherId` / `authorId`

`src/app/api/import/excel/route.ts:116, 120, 139`

```ts
lesson = await db.lesson.create({ data: { …, teacherId: student.classId } })        // :116
await db.grade.upsert({ create: { …, teacherId: student.classId } })                // :120
await db.recommendation.create({ data: { …, authorId: student.classId } })          // :139
```

`student.classId` — идентификатор **класса**, который подставляется в FK на **учителя**. Результат зависит от данных и одинаково плох:

- если учителя с таким id нет → нарушение FK → исключение → 500 и частично применённый импорт;
- если есть (а для маленькой школы `classId` 1..5 почти гарантированно попадает в существующих учителей) → **уроки, оценки и рекомендации тихо приписываются случайному педагогу**. Это ломает авторство, отчёт `type=teacher`, фильтр `teacherId` и журнал аудита.

Нужно брать id текущего админа из сессии (`requireAdmin()` уже вызывается в `POST`) и прокидывать его в импортеры.

### К-3. `mode=replace` в импорте уничтожает базу вместе с журналом

`src/app/api/import/excel/route.ts:52-57`

```ts
if (mode === 'replace') {
  await db.teacher.deleteMany({})      // ← все учителя
  await db.teacherClass.deleteMany({})
  await db.teacherSubject.deleteMany({})
  mode = 'add'
}
```

В схеме у `Lesson.teacher`, `Grade.teacher`, `Recommendation.author`, `ActionLog.teacher` и `Session.teacher` стоит `onDelete: Cascade`. Значит `teacher.deleteMany({})` каскадно сносит **все уроки, все оценки, все рекомендации и весь журнал аудита школы**, а не только педагогов.

Побочный эффект, который делает ситуацию особенно неприятной: среди удалённых — **сам действующий админ**, вместе с его сессией. Поэтому строка 180

```ts
await logAction((await requireAdmin()).teacherId, 'import_excel', …)
```

упадёт с 401 «Требуется вход» — админ увидит ошибку авторизации **после** того, как база уже уничтожена, и даже не получит отчёт об импорте.

Сопутствующие дефекты той же функции:

- `mode` — параметр функции, который мутируется (`mode = 'add'`), чтобы «очистить только один раз». Приём неочевидный и хрупкий.
- В `importStudents` (`:31-34`) та же конструкция очищает **только класс из первой строки**: `deleteMany({ where: { classId } })`, после чего `mode='add'`. Если в листе несколько классов, остальные не очищаются — получается смесь старых и новых учеников. Это не «замена», а наполовину выполненная замена.
- Весь импорт идёт **без транзакции**: падение на 50-й строке оставляет 49 записей и никакого отката.

Смягчающее обстоятельство: из UI `replace` недостижим — `AdminImportExport.tsx:38` всегда шлёт `'add'`, а чекбокс захардкожен `checked={false} disabled`. Но API принимает `mode=replace` от любого админа при прямом вызове, а стейт `importMode` (`:20`) остался мёртвым кодом.

### К-4. Удаление учителя стирает историю школы

`src/app/api/admin/teachers/route.ts:176-182` + `prisma/schema.prisma`

Роут аккуратно удаляет сессии, назначения и `TeacherState` в транзакции, после чего делает `db.teacher.delete()`. Но из-за `onDelete: Cascade` на обратных связях вместе с учителем исчезают:

- **все уроки**, где он указан автором (`Lesson.teacher`), а вместе с уроками каскадом — **все оценки других учителей внутри этих уроков** (`Grade.lesson`);
- **все выставленные им оценки** (`Grade.teacher`);
- **все написанные им рекомендации** (`Recommendation.author`);
- **весь его журнал аудита** (`ActionLog.teacher`).

При этом doc-комментарий в шапке файла (`:10`) утверждает прямо противоположное: *«при DELETE — каскадно удаляются сессии, назначения, TeacherState, **логи остаются**»*. Логи не остаются.

Для журнала успеваемости это недопустимо: увольнение педагога не должно стирать оценки учеников. Нужно либо мягкое удаление (`active: false` у Teacher), либо `onDelete: Restrict`/`SetNull` на `Lesson`/`Grade`/`Recommendation`/`ActionLog` с отдельной проверкой «есть связанные записи → 409», по аналогии с тем, как это уже сделано для классов и предметов (`admin/classes/route.ts:90`).

## 3. Серьёзные дефекты

### С-1. `PUT /api/grades` удаляет комментарий, который не просили трогать ✅ воспроизведено

`src/app/api/grades/route.ts:85`

```ts
if (parsed.data.value === '' && (parsed.data.comment ?? '') === '') {
  await db.grade.delete({ where: { id: parsed.data.id } })
```

`comment` в `gradeUpdateSchema` — **опциональное** поле. Запрос «сбрось оценку, комментарий не трогай» выглядит как `{ id, value: '' }`, и тогда `comment === undefined`, `(undefined ?? '') === ''` → **true** → запись удаляется вместе с ранее написанным комментарием учителя.

| value | comment | удалит? | ожидание |
|---|---|---|---|
| `''` | не передан | **true** | должно быть false — комментарий обязан остаться |
| `''` | `''` | true | верно |
| `'4'` | не передан | false | верно |

Правило очистки должно применяться только когда **оба поля переданы явно пустыми**, а при `comment === undefined` нужно смотреть на текущее значение в БД.

### С-2. `?all=false` работает как `?all=true` ✅ воспроизведено

`src/lib/validators.ts:176-177` — `z.coerce.boolean()` — это `Boolean(value)`, а любая непустая строка истинна:

```
?all="true"  -> true
?all="false" -> true   ← баг
?all="0"     -> true   ← баг
```

Клиент, который честно шлёт `all=false`, получит **всю историю рекомендаций вместо только актуальных**. Нужен `z.enum(['true','false']).transform(v => v === 'true')` или `z.stringbool()`.

Там же: параметр `history` разбирается схемой и деструктурируется в `recommendations/route.ts:33`, но **нигде дальше не используется** — хотя doc-комментарий (`:4`) и сигнатура эндпоинта его рекламируют. Запрос истории по одному ученику не работает.

### С-3. Раздела «Логи» не существует, но он есть в меню

- `src/components/layout/AppShell.tsx:14` — пункт `/logs` показывается **всем** пользователям, не только админу.
- `src/middleware.ts:21` — `/logs/:path*` в matcher.
- Страницы `src/app/(app)/logs/` **нет**, роута `src/app/api/logs/` **нет** (проверено поиском).

Итог: клик по «Логи» → 404. При этом `TEST_REPORT.md` рапортует «Сценарий 12 | Логи | PASS | аудит/пагинация/фильтр ok, секретов нет» — сценарий, которого физически не может быть. Данные в `ActionLog` пишутся, но посмотреть их можно только через экспорт.

### С-4. Логин работает по числовому id, а задуманный вход по фамилии — мёртвый код

`LoginForm.tsx:46-57` подписывает поле «Логин», ставит `inputMode="numeric"` и отправляет его как `teacherId`. То есть учитель должен **помнить свой числовой id в базе**.

При этом в коде лежит полностью готовый, но никем не вызываемый двухшаговый вход:

- `loginStep1Schema` (`validators.ts:6`) — не используется нигде;
- `findTeachersByLastName()` (`auth.ts:119`) с нормализацией регистра, `take: 10` и комментарием «Поиск кандидатов для логина» — **нет ни одного вызова**, эндпоинта `/api/auth/login/step1` не существует.

Либо шаг 1 потеряли при переносе, либо UI не доделали. Сейчас это заметная проблема юзабилити для школы.

### С-5. Экспорт → импорт не делает round-trip, а учителя при этом деградируют

Заголовки, которые пишет `/api/export`, и ключи, которые читает `/api/import/excel`, совпадают лишь частично:

| Лист | Экспорт пишет | Импорт ищет | Результат |
|---|---|---|---|
| Ученики | `fullName`, `classId` | `ФИО`/`fullName`, `Класс`/`classId` | ✅ работает |
| Классы / Предметы | `name` | `Название`/`name` | ✅ работает |
| **Оценки** | `studentName`, `className`, `subjectName`, `lessonDate` | `Ученик`, `Класс`, `Предмет`, `Дата` | ❌ ни одно не совпало → каждая строка «missing fields» |
| **Рекомендации** | `text`, `studentName`, `className` | `Текст`/`Рекомендация`, `Ученик`, `Класс` | ❌ то же самое |
| **Педагоги** | `role`, `isVospitatel` | `Роль`, `Воспитатель` | ⚠️ не совпали → **все админы станут «учитель»**, у всех `isVospitatel=false` |

Плюс `importTeachers:50`: `const password = row['Пароль'] ?? 'changeme123'`. Экспорт (правильно) не выгружает пароли, поэтому при реимпорте **каждому педагогу, включая админов, ставится один и тот же предсказуемый пароль `changeme123`**, без флага «сменить при входе». Это готовый вектор захвата учётки.

Ещё: `row['Класс']` означает **id класса** в листе «Ученики» (`:29` — `findUnique({ where: { id: Number(classId) } })`), но **название класса** в листах «Оценки»/«Рекомендации» (`:111` — `findUnique({ where: { name: … } })`). Одинаковый заголовок, разная семантика.

### С-6. Импорт оценок обходит enum допустимых значений

`gradeSaveSchema` строго ограничивает `value` набором `5/4/3/2/Н/''`. Импорт (`:118-122`) пишет `String(value).trim()` **без какой-либо проверки**. Любая строка из Excel («отл», «A+», «5-») попадёт в `Grade.value` и затем:

- исказит `gradeDistribution` в отчётах;
- попадёт в `numericGrades` только если это `5/4/3/2`, то есть средний балл посчитается по неполной выборке молча.

Ни один импортер вообще не использует zod, хотя схемы уже написаны.

## 5. Мелочи и мёртвый код

- **Неиспользуемые импорты `idSchema`** — `admin/classes`, `admin/subjects`, `admin/teachers`, `admin/responsible` (импортируется, не используется ни разу в каждом из четырёх).
- **Неиспользуемая переменная** `const teacher = await db.teacher.create(...)` — `import/excel/route.ts:60`.
- **Мёртвые схемы**: `paginationSchema`, `loginStep1Schema` (`validators.ts`).
- **Мёртвый стейт**: `importMode` в `AdminImportExport.tsx:20`.
- **Мёртвая ветка**: `middleware.ts:11` проверяет `pathname !== '/'`, но `/` не входит в matcher — условие никогда не ложно по этой причине.
- **`GET /api/import/excel`** всегда возвращает `501 Preview not implemented` — заглушка в проде.
- **Next.js 16 deprecation** (из лога сборки): `⚠ The "middleware" file convention is deprecated. Please use "proxy" instead.` + предложенный кодмод `npx @next/codemod@canary middleware-to-proxy .`. `AGENTS.md` прямо требует реагировать на deprecation-уведомления.

## 8. Дизайн-стенд

Приложение целиком в этой песочнице не поднимается: заблокирован
`binaries.prisma.sh`, движок Prisma не скачивается, и любая страница падает
на `getSession()`. Чтобы работать над внешним видом, добавлен `design/`:

```bash
node design/server.mjs        # http://localhost:3000
```

- `design/index.html` — панель: переключатель экранов и ширины (десктоп / 1024 / планшет 834 / телефон 390, брейкпоинт приложения — 760px).
- `design/screens.html` — разметка экранов (вход, журнал, ученики, отчёты, воспитание, админка), скопированная из `.tsx` 1:1 по классам `gg-*`.
- Стенд подключает **рабочий** `src/app/globals.css`, поэтому правки стилей идут в боевой файл, а не в копию, — расхождения по CSS не возникает.

Важно: `DESIGN_PACK.md` (собран 2026-09-09) описывает прежнюю пастельную
glassmorphism-тему. Фактический `globals.css` уже переписан на светлую
iOS-подобную тему с токенами `--gg-*` и акцентом `#0071e3`, плюс появились
классы `gg-stat*`, `gg-badge`, которых в паке нет. Перед следующим редизайном
пак стоит пересобрать, иначе он уведёт в сторону.
